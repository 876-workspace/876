# Implementation Plan: 876 Projects Phase 13 — Workflow Automation & Blueprints

- **Run ID:** `2026-09-16-projects-phase-13` · **Branch:** `feature/projects-phase-13-automation` · **Status:** `PLANNED`

## Binding decisions
1. **Transitions** (`projects_workflow_transitions`): tenant, `workItemTypeId` nullable (null = all types), `fromStateKey` (nullable = any), `toStateKey`, `name`, `requiredPermission` nullable (an existing permission key only), `requiredFieldKeys` string[] (layout field keys), `requiresComment` bool. If **no** transition rows exist for a type, all state changes remain allowed (backwards compatible). Once any exist, a state change must match one — enforced in the issues service, registered error `projects/transition-not-allowed` / `projects/transition-requirements-unmet` (param lists missing).
2. **Blueprint** = the set of transitions for a type, edited as one resource (`GET/PUT /workflows/:workItemTypeId/blueprint`), versioned by `updatedAt`; no separate table.
3. **Automation rules** (`projects_automation_rules`): tenant, optional `projectId`, `name`, `enabled`, `trigger` ∈ `work-item.created | work-item.updated | work-item.state-changed | phase.completed | due-date.approaching | time-entry.submitted | budget.threshold-reached`, `conditions` (same condition vocabulary as layout rules, reuse `evaluateLayoutRules` condition matcher — export a `matchesConditions` from `packages/projects/src/layout-rules.ts`, do not write a second matcher), `actions[]` ∈ `set-field | assign | add-label | remove-label | create-reminder | create-event | notify | call-webhook | create-sub-item`, each with a typed params schema.
4. **Execution is durable and asynchronous**: domain services append `projects_automation_events` (outbox, same transaction as the mutation). A worker (`src/workers/automation.worker.ts`, run by the existing worker/cron entry if one exists; otherwise an internal-key `POST /internal/automation/drain` route invoked by Vercel cron) claims batches with `FOR UPDATE SKIP LOCKED`, evaluates rules, performs actions, records `projects_automation_runs` (rule, event, status `succeeded|failed|skipped`, error code, attempt, timings). Max 5 attempts with backoff; idempotent per (rule, event).
5. **Loop guard**: actions performed by automation carry `actor = automation:<ruleId>`; events caused by automation carry `causationDepth`; depth > 3 is skipped and recorded.
6. `due-date.approaching` and `budget.threshold-reached` are produced by the drain sweep (scan, dedupe per item per day), not by timers.
7. `notify` records an in-app notification row only (no email — email belongs to 876 Communications; deferred). `call-webhook` posts JSON with HMAC-SHA256 signature header `x-876-signature: t=<ts>,v1=<hex>` using a per-rule secret stored via `@876/core/crypto/secure-field`; 10s timeout; response code recorded.
8. Runs history is readable in app and Console.

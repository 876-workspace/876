## Part A — Work extension (`apps/work-api`, `packages/work`)

### Schema change

`WorkReminder` (`apps/work-api/prisma/schema/work.prisma`) gains:

```prisma
remindAt         DateTime? @map("remind_at")          // was required
offsetMinutesBeforeDue Int? @map("offset_minutes_before_due")
channel          String    @default("in-app")
```

`packages/work/src/types.ts` (single source of truth — the work-api
`createReminderBodySchema` / `updateReminderBodySchema` alias these schemas,
so routes, controller, and both SDK entrypoints pick the fields up with no
second contract):

- `workReminderSchema`: `remindAt` nullable, plus `offsetMinutesBeforeDue`
  (`int 0..525600`, nullable, required key) and `channel` (trimmed string
  1..120, required key).
- `createWorkReminderInputSchema`: `remindAt` optional/nullable, `offset…`
  optional/nullable, `channel` optional, plus `superRefine` rejecting a payload
  where both timing legs are null.
- `updateWorkReminderInputSchema`: adds nullable `remindAt` /
  `offsetMinutesBeforeDue` and optional `channel` (so one leg can be cleared).
- `packages/work/src/resources/reminders.ts` needed **no** hand edit: it
  serializes the Zod-typed input as JSON and validates responses against
  `workReminderSchema`, so both fields flow through automatically.

### Validation: service-level + Zod, backed by a DB CHECK

I chose **service-level validation as the enforcing layer, with a DB CHECK as
backstop**:

- Zod `superRefine` on create returns `work/invalid-request` through the normal
  envelope (client-safe value, 422), mirroring `alerts.service.ts` trigger
  validation. A bare DB constraint would surface as an unexpected Prisma
  failure (500) instead.
- Zod cannot see the stored row, so `reminders.service.ts` `update()`
  computes the merged next state and returns `getError('work/invalid-request')`
  when both legs would end up null (clearing the last leg). `repository.update`
  is never called in that case (tested).
- Migration also adds
  `CONSTRAINT "work_reminders_timing_check" CHECK ("remind_at" IS NOT NULL OR
  "offset_minutes_before_due" IS NOT NULL)` so non-API writers cannot create an
  unfireable reminder. Safe for existing rows: `remind_at` was `NOT NULL`, so
  all existing rows satisfy it.

`channel` stays **optional** (not `.default()`) in the create schema so the
existing CRM caller typechecks untouched; the service applies
`input.channel ?? 'in-app'` and the column default covers direct writes.

### Migration SQL (hand-written, in full)

`apps/work-api/prisma/migrations/20260919000000_reminder_offset_and_channel/migration.sql`
(timestamp matches the existing 14-digit folder format):

```sql
-- Extend WorkReminder with relative scheduling and delivery channel.
-- Additive plus widening: existing rows keep their absolute remind_at, and the
-- new timing CHECK is satisfied by every existing row because remind_at was
-- previously NOT NULL. New rows default to the in-app channel.

ALTER TABLE "work_reminders" ADD COLUMN "offset_minutes_before_due" INTEGER;
ALTER TABLE "work_reminders" ADD COLUMN "channel" TEXT NOT NULL DEFAULT 'in-app';
ALTER TABLE "work_reminders" ALTER COLUMN "remind_at" DROP NOT NULL;
ALTER TABLE "work_reminders" ADD CONSTRAINT "work_reminders_timing_check" CHECK ("remind_at" IS NOT NULL OR "offset_minutes_before_due" IS NOT NULL);
```

### Serializer / routes / OpenAPI

- Serializer is `serialize()` inside `reminders.service.ts` (this module has no
  separate `serializers.ts`/`docs.ts` — verified by grep); it now emits
  nullable `remindAt`, `offsetMinutesBeforeDue`, `channel`.
- Routes/controller unchanged: they parse via the aliased Zod schemas.
- There is **no OpenAPI/docs layer in `apps/work-api`** (grep for
  openapi/OpenAPI/docs.ts finds nothing outside generated Prisma comments), so

### Null-safety fallout inside `apps/work-api` (same-scope, typecheck-driven)

- `reminders.repository.ts`: cursor anchors typed `Date | null`; `gt`/`lt`
  branches only when the anchor is non-null, equality branches match nulls.
- `notification-outbox.service.ts`: offset-only reminders return no
  occurrences (the absolute due scan cannot fire them; they resolve host-side).
- `my-work.service.ts`, `resource-work.service.ts`: range filters now require
  `remindAt !== null`.
- Known limitation (not fixed): cursor pagination from a non-null anchor can
  skip offset-only rows on later pages (`gt` excludes NULLs while ASC sorts
  them last). Reminder volumes make this unlikely to bite; flagging it rather
  than redesigning pagination here.

## Part B — Projects adapter and convergence (`apps/projects-api` only)

### Adapter exports (`apps/projects-api/src/providers/work.ts`)

- `workClient()` — `create876WorkServiceClient` from `@876/work/service`
  (**service** tier: first-party service→service; env `WORK_API_URL` /
  `PROJECTS_API_876_KEY`, mirroring `finance.service.ts` billing precedent).
- Context builders `projectsIssueWorkContext` /
  `projectsMilestoneWorkContext` / `projectsEventWorkContext` producing
  `{ service: 'projects', resource: 'issue'|'milestone'|'event', id }`.
- `workErrorToProjects(error)` mapping onto the **existing** registry only:
  `work/tenant-not-found` → `projects/tenant-not-found`,
  `work/invalid-request` → `projects/invalid-request`,
  `work/reminder-not-found` → `projects/reminder-not-found`, everything else
  (incl. null/undefined) → `projects/internal-error`. Upstream code/message are
  logged; callers get the stable Projects value, never a throw.
- **No fitting code exists** for connection/auth/unavailability failures
  (`work/connection-forbidden`, `work/unauthorized`, `work/not-configured`,
  `work/identity-unavailable`, `work/internal`, …): the Projects registry has
  no `work-unavailable` equivalent, so per instructions I invented nothing and
  they collapse to `projects/internal-error`. Say so explicitly here.
- `apps/projects-api/package.json` gains `"@876/work": "workspace:*"`.

### Explicit field mapping (Projects → Work)

| Projects | Work (after Part A) |
| --- | --- |
| `issueId` / `milestoneId` / `eventId` | `context` triple via the three builders; precedence issue → milestone → event (same order the old due resolver used) |
| `remindAt` (nullable) | `remindAt` (nullable) |
| `offsetMinutesBeforeDue` | `offsetMinutesBeforeDue` |
| `channel` | `channel` (create; Projects update contract has no channel field, unchanged) |
| five inline recurrence columns | `WorkRecurrenceRule` via `reminders.recurrence.set` on create/update, `recurrence.clear` on null, `recurrence.retrieve` on read; freq lower→UPPER, `byWeekday` 0–6 (Sun–Sat) → `SU..SA`, `until`→`untilAt`, `count`→`count`, `timeZone: 'UTC'` (Projects stores none) |
| `createdBy` | `createdBy` **and** `userId` (Work requires `userId`; Projects has none, creator fills both) |
| `active` | `status`: `true`→`SCHEDULED`, `false`→`CANCELLED`; read back as `status !== 'CANCELLED'` |
| `tenantId` (serialized) | resolved Projects tenant id (Work rows carry `organizationId`; 1:1 tenant mapping preserves the contract shape) |

Fields with no clean destination (reported, not dropped silently):

- **Work requires `title`; Projects has none.** Derived deterministically
  (`Issue reminder` / `Milestone reminder` / `Event reminder` / fallback
  `Projects reminder`); never surfaces in the Projects contract.
- **`timeZone`**: Work accepts one, Projects stores none → always `'UTC'` on
  rule creation, rule's own zone kept on merge-updates.
- **Update-target semantics changed**: the old columns were independent, Work
  holds one triple, so a target patch **replaces** the target (setting
  `milestoneId` clears a previous `issueId`) instead of merging; merging would
  shadow the second id behind precedence.
- **Work rule extras** (`byMonthDay`, `byMonth`, `weekStart`) are ignored on
  read/expand — Projects-created rules never set them.
- **Orphaned rule on failed create**: if `recurrence.set` fails after the
  reminder was created, the error is returned as a value with no compensating
  delete (single-shot endpoint, no transaction across the service boundary).
- **Offset resolution stays host-side** (ADR-019): `retrieveIssueDueDate` /
  `retrieveMilestoneTargetDate` / `retrieveEventStart` remain in
  `calendar.repository.ts`; only the six `prisma.reminder.*` functions moved.
- **`projects_reminders` rows are dropped, not backfilled**: Work is a separate
  database/service, so no SQL backfill is possible; see migration below.

### Call sites moved (all of them)

Every `prisma.reminder.*` call lived in `calendar.repository.ts`
(`createReminder`, `listRemindersByCreator`, `listActiveReminders`,
`retrieveReminder`, `updateReminder`, `deleteReminder` — all deleted with their
param types). The service (`calendar.service.ts`) now calls
`workClient().reminders.{list,retrieve,create,update,delete}` plus
`reminders.recurrence.{retrieve,set,clear}`; listing pages (20×100, same shape
as the CRM caller) and filters to `context.service === 'projects'` plus
`createdBy` so other services' reminders for the same user never leak in.
Cross-service rows on retrieve/update/delete map to
`projects/reminder-not-found`. No repository calls `workClient()` (verified by
grep). Serializers: `ReminderRow` deleted; `serializeReminder` /
`serializeDueReminder` now take `(WorkReminder, tenantId, rule)`; new
`workReminderTarget`, `serializeWorkRecurrence`, `workRuleToRecurrenceRule`.

Removed `model Reminder` from `calendar.prisma` and its relation fields on


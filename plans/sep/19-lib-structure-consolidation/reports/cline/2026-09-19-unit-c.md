# Unit C — one apps directory, driven by configuration

Date: 2026-09-19
Branch: `refactor/lib-structure-consolidation`

## What changed

### Owner — `packages/core/src/lib/apps-directory.ts` (new)

`buildAppsDirectory({ current, currentUrl })` returns plain `AppDirectoryEntry[]`
(`{ name, url, current? }`), which satisfies `AppSwitcherApp` structurally — the
three shells type `apps: AppSwitcherApp[]`, so `tsc` proves the contract at each
call site (`apps/crm/src/components/shell/shell.tsx:44`).

- **One list, ordered in code**: `APP_ORDER` is a declared array
  (`as const satisfies readonly PlatformAppName[]`); `APP_NAMES` and
  `appOrigins()` are `Record<PlatformAppName, …>`, so registering a new app in
  `PLATFORM_APP_SLUGS` is a typecheck error until it is named and given an
  origin. Nine apps: consumer, Billing, Couriers, CRM, Projects, Invoice,
  Enterprise, Console, Commerce.
- **No fallback origin**: each entry's url comes only from
  `NEXT_PUBLIC_<APP>_URL`. Unset or blank/whitespace-only → the app is omitted.
  The current app is always present at `currentUrl ?? '/'` whatever its own
  variable says.
- No `@876/ui` import; no `server-only`; `process.env.NEXT_PUBLIC_*` are read as
  static member expressions inside the function so Vitest can stub them and
  Next can inline them at build time. Values are trimmed, not otherwise
  normalised (no trailing-slash rewriting — out of scope).

Display names: `876`, `876 Billing`, `876 Couriers`, `876 CRM`, `876 Projects`,
`876 Invoice`, `876 Enterprise`, `876 Console`, `876 Commerce`. The `876 X`
form follows the deleted copies; Console's own inline switcher still calls
itself `Console` (see "Unverified / follow-ups").

### Registry — `packages/core/src/lib/platform-apps.ts`

`PLATFORM_APP_SLUGS` extended with the three apps the directory needs and the
registry lacked: `crm: '876-crm'`, `projects: '876-projects'`,
`commerce: '876-commerce'`. The exhaustive `PLATFORM_FEATURE_PREFIXES` record
gained matching entries (`crm`, `projects`, `commerce`) — each equals the prefix
the existing fallback derivation already produced (`'876-crm'` → `crm`,
confirmed against `apps/api/src/seeds/features.ts:512`), so this is
behaviour-neutral. Registry untouched otherwise.

### Package export — `packages/core/package.json`

`"./apps-directory"` → `./src/lib/apps-directory.ts`, placed alphabetically
between `./api` and `./auth/*`.

## Unverified / follow-ups

1. **No app test suite run** for `@876/crm-app`, `@876/projects-app`,
   `@876/couriers-app`. The change is a `layout.tsx` prop; no test in those apps
   references `apps={…}` or `AppSwitcher` (only the shells consume it), so the
   coverage that matters here is typecheck + structure, both green. Couriers'
   `apps-directory.test.ts` was deleted with its module and its scenarios live
   in the core suite.
2. **No runtime/browser render check** of the switcher in any of the three apps.
3. **Dev-env wiring is now visible**: `scripts/setup-dev-env.mjs`'s
   `envPlanFor` writes only a subset of these origins (couriers gets
   `COURIERS_URL`/`APP_URL`/`BILLING_URL`; crm gets `CRM_URL`/`APP_URL`;
   projects gets `PROJECTS_URL`/`APP_URL`). The switcher will therefore omit
   siblings that the old hardcoded lists showed, in local dev as in production.
   That is the intended trade (omission over a guessed origin), but if dev
   parity is wanted, `envPlanFor` is where to add them. Not changed here —
   out of this unit's scope.
4. **Two consumer-origin variables coexist**: the new module reads
   `NEXT_PUBLIC_APP_URL` for the consumer entry (the name the consumer app and
   the three migrated apps declare), while Console's inline switcher still reads
   `NEXT_PUBLIC_876_APP_URL` (`apps/console/src/components/shell/topbar-actions.tsx:11`).
   Console's migration should settle on one; nothing here depends on it.
5. **Pre-existing prettier debt** in two files this unit touched only partially:
   `apps/projects/src/app/(app)/layout.tsx` (36 diff lines vs prettier at
   `HEAD`) and `scripts/app-structure-lib-ratchet.json` (24, the generator emits
   expanded arrays prettier would collapse). Both fail `prettier --check` at
   `HEAD` already; I left the unrelated formatting alone rather than adding
   diff noise, so `pnpm format:check` remains red for reasons unrelated to this
   unit.
6. **No `.env.local` values were set** for the new variables, per the brief.
   `pnpm check:env` reports them as `unset but optional` until a developer or
   deployment configures them.

## Phase B

- Added `apps/billing-api/src/modules/documents/repositories/invoices/update.test.ts`.
  It covers the reused input schema, malformed/empty line arrays, DRAFT total
  recomputation and atomic replacement, metadata-only updates, every
  non-DRAFT lifecycle rejection, tenant isolation, line-preparation failure,
  and empty updates.
- The existing implementation was retained. It already correctly uses
  `buildDocumentLines` and `calculateDocumentTotals`, replaces lines in one
  transaction, and permits replacements only for DRAFT invoices.
- The update contract intentionally remains additive only for `lines`:
  customer, currency, price-list, and document-level adjustments are
  creation-time snapshots and do not have a safe update lifecycle policy.

## Phase C

- Chose option (a): each app retains its own already-diverged
  `DocumentCreateForm`, now with `mode`, `initialDocument`, and an optional
  typed submit-handler prop. No third form or cross-app de-fork was created.
- Both edit pages now render their host's `DocumentCreateForm` at the same
  page chrome and form width as its new-invoice page. The obsolete
  `invoice-edit-form.tsx` was deleted from both apps; a repository grep finds
  no remaining invoice-edit-form import.
- DRAFT mode exposes line editing and submits `lines`; restricted modes hide
  the editor and send only due date, notes, terms, and reference number.
  Failed submissions remain in-context beside the live form.
- Added five edit-mode tests to each app's existing create-form test file:
  DRAFT editor, restricted omission, payload, inline failed submit/value
  retention, and restricted payload.
- Billing invoice detail now calls `getBilling().invoices.retrieve()` directly,
  so `as unknown as InvoiceDetail` is removed. The remaining legacy
  `resolveInvoice` path is not used by that page.

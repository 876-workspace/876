# 876 Invoice — v1 implementation brief (reinforced)

Answers to the three open questions Codex raised, promoted to **closed
architectural decisions**. Read together with `.claude/rules/platform-services.md`,
`.claude/rules/sdk-conventions.md`, and `.claude/rules/app-structure.md`.

> Build 876 Invoice as a first-party, independently entitled 876 product whose UI
> is intentionally thin over the shared Billing financial data plane. Reuse the
> shared 876 session and platform organization context. Declare embedded finance
> through the existing provisioning manifest system. Do not create an Invoice
> database or API. For v1, prove the architecture with one live, read-only
> `/invoices` path. Stop after that vertical slice.

## Product intent

876 Invoice is a product surface, not a financial service. It is **not** a new
financial database, a child module of Billing, another auth realm, a wrapper API
over Billing, or a fork of the Billing codebase.

```
876 Identity / Core   →  identity + app entitlement
        ↓
876 Invoice (apps/invoice)
        ↓  tenant-scoped Billing client
876 Billing API  →  shared finance workspace (customers · invoices · payments)
```

The app owns the Invoice UX. Billing owns the financial records.

## Decision 1 — Auth: reuse `876-session`. CLOSED.

Verify with `@876/core/auth/session-cookie` exactly as the other first-party apps
do. `src/lib/auth/` holds `session-cookie.ts` (re-export), `session.ts`
(`cache()`d cookie → verifier → normalized app session, `redirect('/login')` when
`ensureSignedIn`), `guards.ts`, `context.ts`.

Forbidden: `invoice-session`, NextAuth, another WorkOS integration, Invoice users,
Invoice passwords, an Invoice session store, an Invoice auth API. The Billing SDK
is not the auth layer — it consumes an already-resolved identity.

Invoice hosts its **own** embedded login and sign-up — it is a standard product,
not a satellite of the consumer app. `@876/ui/auth` runs against the app's own
thin `/api/auth/[...path]` bridge, which attaches `INVOICE_API_876_KEY` and
declares `X-876-Realm: enterprise`, so the API seals the session cookie on
Invoice's own origin. Redirecting to another app's login is not acceptable.

Social sign-in offers exactly **Google, Outlook (`microsoft`), and Apple** —
the three the platform supports. Each origin's `{origin}/callback` must be
registered in the WorkOS dashboard, and `callback/route.ts` exchanges the code
server-side. A social sign-up creates an account with no organization, which is
precisely why `/onboarding` exists.

`login/`, `callback/`, `auth/complete/route.ts`, `no-access/` are standard
ecosystem plumbing. `auth/complete` resolves the relative return-to and
redirects; **no financial provisioning logic there**.

### Org sign-up is part of auth, not a later feature

Per `product-org-signup.md`: an account that can authenticate must be able to
onboard. A signed-in account with **no organization** goes to `/onboarding`,
which creates the org (`platform.organizations.create`) and activates the
`876-invoice` subscription. `/no-access` is reserved for an account that has an
org but is not permitted — it is an authorization answer, never "no org yet".

Memberships are resolved **live** from the platform, not from the sealed cookie,
so a just-created org is visible on the next request without a re-login. An
account that already has an org reuses it rather than creating a second.

## Decision 2 — Gate on the `876-invoice` subscription. CLOSED.

Three distinct things; never conflate them:

- `876-invoice` subscription → access to the **Invoice product**
- `876-billing` subscription → access to the **Billing product**
- Billing finance workspace → **infrastructure** used by finance-enabled products

A valid org state is: Invoice YES, Billing NO, workspace YES.

Order of operations:

```
authenticate → resolve org → check 876-invoice subscription
             → if entitled, ensure Billing workspace → open Invoice
```

Never "workspace exists ⇒ Invoice access". The authoritative gate is the private
`(app)/layout.tsx`: `requireValidSession` → `getInvoiceContext()` → redirect
`/no-access` when the context is null or `accessStatus` is neither `active` nor
`trialing`. RSC-layout gating only — **no `proxy.ts` / `middleware.ts`**
(root `CLAUDE.md` → "Routing — no proxy.ts / middleware.ts"; OpenNext cannot run
Node middleware and the Cloudflare build fails outright).

### Do not provision Billing from the Invoice app

The provisioning control plane already exists. Declare the dependency in
`apps/api/src/seeds/provisioning.ts` and let Core emit the durable
`finance_connection.ensure` event:

```ts
{ slug: '876-invoice', financeDependency: 'embedded',
  financeScopes: ['billing.invoices.read'] }
```

Never write `if (!billingWorkspace) await createBillingWorkspace()` in the app.

**Least privilege, staged.** v1 requests `billing.invoices.read` only. Add
`customers.read` / `items.read` / `invoices.write` when `/invoices/new` lands;
`payments.*` when payment recording lands. Do not pre-grant future scopes.

### Provisioning lag is not "unsubscribed"

An org can be entitled a moment before `finance_connection.ensure` completes.
Surface "We're setting up your Invoice workspace. Please try again shortly." —
never `/no-access?reason=subscription`. No polling machinery in v1.

## Decision 3 — Scope: bare shell + live `/invoices` list. CLOSED.

v1 = bootstrap, shared session auth, login/callback/auth-complete, entitlement
gate, workspace resolution, app shell, and `/invoices` reading **live** Billing
API data. That single read path is the acceptance test for the whole
architecture.

Excluded from v1: invoice creation/edit/delete/finalize/void/send, PDF, customers
CRUD, payments, tax config, recurring invoices, reminders, estimates, credit
notes, import/export, dashboard analytics, an Invoice database, an Invoice API.
`customers/` and `settings/` may exist as placeholder pages.

### Invoice context is not a copy of Billing's

Billing's context carries Billing-local tenant/permission resolution because
Billing owns its workspace. Invoice does not. Its context is:

```ts
{ userId, orgId, orgName, orgSlug, role,
  organizations: Array<{ id; name; slug; role }>,
  accessStatus: 'active' | 'trialing' | 'blocked' | 'none' }
```

Resolved as: session → `platform.memberships.listRouting({ userId, status:
'active' })` → pick the session org (else first active) →
`platform.subscriptions.retrieve({ organizationId, appSlug: INVOICE_APP_SLUG })`.
No `billingTenantId`, no Invoice roles, no Invoice tenant row.

### Data path — the only sanctioned one

```
Invoice app → @876/client (app: 'invoice') → @876/billing
            → Authorization: Bearer …, x-billing-organization-id
            → GET /api/v1/invoices → Billing API → Billing datastore
```

Never `fetch(`${BILLING_API_URL}/api/v1/invoices`)`, never
`service.invoices.list()`, never `prisma.invoice.findMany()`. Do **not** copy
Billing's own invoice-list implementation — Billing may reach its owned internals;
Invoice must use the public tenant contract.

`packages/client/src/composers/invoice.ts` exposes a deliberately narrow surface —
`{ ...core, invoices: billing.invoices }` — and grows one resource at a time.
`app: 'invoice'` is a member of the `ServerClientOptions` union and the exhaustive
`server.ts` switch.

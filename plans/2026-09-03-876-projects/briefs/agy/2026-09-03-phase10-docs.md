## 2. What to write

### 2.1 `docs/architecture/0NN-876-projects.md`

Use the next free number in `docs/architecture/` and match the format of the
existing records exactly. Cover:

- what 876 Projects is, in two or three sentences;
- **why the issue key prefix and counter live on the Project** rather than a
  team, and the consequence that every issue belongs to a project with a
  per-tenant **Triage** project (`TRI`) absorbing homeless work;
- that an issue **keeps its identifier when moved** between projects;
- how an issue number is allocated: a single atomic increment that returns the
  post-increment value, so two concurrent creates cannot collide — and why a
  read-then-increment would be a race;
- the bounded-context placement: its own datastore, referencing core 876
  entities by opaque ID with no cross-database foreign key;
- the caller tiers — `session` for the app, `operator` for Console — and that a
  capability is implemented once and merely routed again;
- timestamps as Unix seconds (`BigInt` in the database, `number` in JSON) and
  enum-like columns as `TEXT` + `CHECK` rather than Postgres enums, with the
  reason;
- errors as values from day one.

### 2.2 `docs/876-projects.md` — the operator/developer guide

- ports (app **3008**, API **4030**) and the platform app slug `876-projects`;
- the environment contract for both workspaces, naming which values are secret;
- how to run it locally (`pnpm dev:projects`), and that `projects-api` also
  starts with every console dev script;
- how to apply migrations, and that migrations use the **direct** Neon endpoint
  because the pooler cannot hold `prisma migrate`'s advisory locks;
- the permission catalog and which module each key gates;
- what is **not** built yet, taken from the module catalog's `available: false`
  entries and the orchestrator reports.

### 2.3 `packages/projects/README.md`

Short. The bounded roots, the three entrypoints and when to use each, one usage
example per entrypoint copied from real signatures, and the rule that resource
verbs are `create`/`retrieve`/`list`/`search`/`update`/`delete`.

## 3. House style — these are rules, not preferences

- **No wordy subheading paragraphs.** Do not put an explanatory sentence under a
  heading restating what the table below already shows.
- Prefer a table to prose for anything enumerable.
- Explain **why**, not what the code obviously does.
- British-neutral, plain, specific. No marketing register, no "seamlessly", no
  "robust", no emoji.
- Every code block must be copy-pasteable and real.
- Do not document a file path, script, env var, permission key or route that you
  have not opened and confirmed.
